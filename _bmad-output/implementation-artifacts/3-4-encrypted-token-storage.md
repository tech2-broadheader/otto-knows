# Story 3.4: Encrypted persistent connector-token storage

Status: in-progress — Tasks 1–5 done; Task 6 manual check needs a real Supabase project + Google OAuth credentials

## Story

As a Pro user who connected Google Calendar,
I want my Google access to be stored securely and survive server restarts,
so that Otto keeps reading my calendar without me reconnecting, and my credentials are never exposed.

## Acceptance Criteria

1. The in-memory token store is replaced (in production) by a Postgres-backed store: table `connector_tokens` keyed by `(user_id, provider)` with `ciphertext`, `iv`, `key_version`, `expires_at`, `updated_at`. RLS enabled with **no** client policies (service connection only).
2. Token bundles are encrypted with **AES-256-GCM** (`node:crypto`, authenticated) using `TOKEN_ENCRYPTION_KEY` (32 bytes, base64) read through the typed config module; a fresh random 12-byte IV per write; `key_version` stored for future rotation. Tampered or wrong-key ciphertext fails closed (treated as "not connected"), never returns garbage.
3. Token material is never logged or returned to clients; each read / write / delete is recorded in a server `audit_events` table (user id, entity `connector_token`, action, timestamp — no token data).
4. `POST /api/connectors/google/disconnect` deletes the stored token; `/api/account/delete` purges the user's tokens (and audit rows) before deleting the auth user.
5. When the database or key isn't configured: non-production falls back to in-memory (dev convenience); production returns a typed "not configured" error instead of silently keeping tokens in memory.
6. Tests: crypto round-trip, unique IVs, tamper/wrong-key failure, bad key length rejected; encrypted store set/get/delete against an in-memory row store, including expiry passthrough and fail-closed on corrupt rows; config accepts/rejects the key.

## Dev Notes

- **Why node:crypto, not a new library:** AES-256-GCM is a standard primitive in Node's built-in crypto — no hand-rolled cipher (CLAUDE.md §11) and no new dependency. Mobile uses `@noble/ciphers` for the same algorithm on device.
- The server DB connection (`DATABASE_URL`) bypasses RLS by design (see `apps/web/src/server/db/client.ts`); RLS with no policies blocks every anon/authenticated client path.
- Out of scope: token refresh on 401 (existing TODO in calendar route), OAuth `state` verification (existing TODO), revoking the grant at Google on disconnect (follow-up).
